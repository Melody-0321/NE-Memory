# 分词器 + 向量检索综合评估

## 一、当前 1+2gram 分词器分析

### 当前实现

[text-utils.js](file:///d:/SillyTavern/xm/ne-memory/src/core/engine/text-utils.js#L22-L48) 的 `tokenize()` 已实施 v4.2 的 1+2gram 方案：

- CJK 字符 → 单字 token + `^` 前缀双字 bigram token
- 英文/数字 → 连续字母串（小写）
- 标点/空格 → 跳过

```
"铁匠铺" → ['铁','匠','铺','^铁匠','^匠铺']
"hello"  → ['hello']
```

### 缺陷

| 问题 | 示例 | 影响 |
|------|------|------|
| **Token 膨胀** | 20 字中文 = 39 tokens (2n-1) | avgDocLen 被抬高 → 长度归一化失真 |
| **无意义 bigram 噪音** | `她走进了房间` → `^了房, ^间看` 等 | 跨文档伪匹配，IDF 被噪音稀释 |
| **无法识别专名** | `安然` → `安 + 然 + ^安然`，但 `安然地` 也生成 `^安然` | 同名不同语境误匹配 |
| **语义断裂** | `摔门` vs `愤怒离开` → 零 token 重叠 | **BM25 无法召回（核心盲区）** |

### 已缓解的问题

| 问题 | 缓解机制 | 说明 |
|------|---------|------|
| 停用词（的、了）| IDF 自然降权 | "了" 出现在多数文档中 → DF 高 → IDF 低 → 评分弱 |
| 短词匹配度 | 双字 bigram | "铁匠" 匹配 "铁匠铺" 中的 `^铁匠` |

**结论：1+2gram 在 BM25 的词面匹配层面是 "够用的"。06-26 冒烟测试全部通过证明了这一点。**

## 二、WASM jieba 评估

### 可行性

| 维度 | 详情 |
|------|------|
| NPM 包 | `jieba-wasm` (cppjieba via emscripten) |
| 体积 | ~8MB (WASM binary + 词典) |
| 加载方式 | 异步 `await`，需在首次 SmartPush 前完成 |
| 浏览器兼容 | ✅ (SillyTavern 环境支持 WASM) |
| API 调用 | 0（纯本地） |

### 收益

| 问题 | jieba 能否解决？ |
|------|-----------------|
| Token 膨胀 (2n-1 → ~1n) | ✅ 部分缓解。20 字中文 ≈ 13-15 tokens |
| 无意义 bigram 噪音 | ✅ 消除。只输出有意义的词 |
| 专名识别 | ✅ 部分。`安然` → `['安然']`，但 `安然地` → `['安然','地']`，仍匹配到 `安然` |
| **语义断裂** (`摔门` vs `愤怒离开`) | ❌ **不能解决**。词面仍零重叠 |

### 代价

| 代价 | 量化 |
|------|------|
| 首次加载延迟 | +1-2 秒 (8MB WASM + 词典初始化) |
| 内存增量 | +15-30 MB (WASM runtime + 词典 Trie) |
| 分词延迟 | +5-15 ms / 条 (vs 当前 < 1ms) |
| 构建复杂度 | 新增异步依赖、初始化流程、错误处理 |
| 退化路径 | WASM 加载失败 → fallback 到 1+2gram（代码复杂） |

### 致命评估

jieba 能解决的缺陷（噪音 bigram、token 膨胀）是**精度微调**级别。它不能解决的缺陷（语义断裂）是 **召回率质变**级别。

**用 8MB WASM + 2 秒加载换来精度微调，不如用一个 API 调用换来召回率质变。**

## 三、1+2gram + 向量检索 vs jieba + 向量检索

这两条路的差异非常清楚：

| | 方案 A：1+2gram + 向量 | 方案 B：jieba + 向量 |
|---|---|---|
| 开发量 | 新增 embedding.js + retrieval-fusion.js | 新增 embedding.js + retrieval-fusion.js + jieba 集成 |
| WASM 依赖 | 无 | 8MB |
| 内存 | +1.2MB（向量） | +16-31MB（向量 + WASM + 词典） |
| 首次延迟 | 向量冷启动 ~1-3s | 向量冷启动 ~1-3s + jieba 加载 ~1-2s = 2-5s |
| BM25 精度 | 基线（够用） | 基线 + 微调（去除噪音 bigram） |
| 语义召回 | ✅ 质变 | ✅ 质变 |
| 维护成本 | 低 | 中（WASM 版本、词典更新、fallback 路径） |

**方案 A 和方案 B 的语义召回增益相同（都来自向量检索）。方案 B 的额外成本（WASM + 内存 + 维护）换来的只是 BM25 精度的微调。**

---

## 四、建议优先级

```
优先级 1 (P0)：BM25 + 向量混合检索    ← 召回率质变，无额外基础设施依赖
优先级 2 (P2)：WASM jieba 分词器      ← 精度微调，ROI 低
```

两者**不应一起做**。原因：

1. **jieba 的 BM25 改进效果无法在向量检索存在时被有效测量** — 向量检索覆盖了 jieba 的大部分盲区，jieba 的边际收益会被淹没
2. **调试复杂**：同时改两个检索面，出问题时无法判断是 jieba 还是向量的 regression
3. **设置用户预期**：如果用户配了 embedding API，召回率已经显著改善。再用 jieba 的边际收益几乎不可感知

**策略**：先做混合检索。如果用户反馈中持续出现"BM25 回退时召回差"的 case（即 embedding API 不可用时），再做 jieba。

---

## 五、更新 BM25+向量方案

原有方案不变，但加一条：**在 embedding API 不可用时，仍使用当前 1+2gram tokenizer + 纯 BM25。**

向量检索的引入使得 jieba 的必要性大幅下降，因为：
- 有向量检索时 → 语义匹配由向量保证，BM25 只需做关键词补强 → 1+2gram 够用
- 无向量检索时 → 回退到纯 BM25（当前行为，已验证可用）
